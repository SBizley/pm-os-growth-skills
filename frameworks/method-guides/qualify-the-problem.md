# Qualify the Problem

*Understand · Ongoing · Understanding the problem*

# **Purpose**

Validate *why* a problem exists, what pain it creates, and how customers describe it - through direct human evidence rather than data points.

# **When to Use**

- After quantifying *what’s happening* but before ideation
- When you need rich stories that explain user behaviour
- To triangulate numbers with context and emotion

# **How to Run**

**Duration:** 1–2 hours per synthesis session

**Materials:** Interview notes, call recordings, survey responses, observation data

# **Steps:**

1. Gather qualitative signals: interviews, usability tests, sales/support transcripts.
2. Identify language users use to describe the pain - note emotions and expectations.
3. Cluster similar quotes into themes (frustrations, needs, blockers).
4. Rank by **intensity of pain** and **repetition across users**.
5. Combine with quantitative metrics to form a holistic problem narrative.

# **Example**

> “I refresh the payout dashboard every hour” → shows anxiety and lack of trust in system feedback.
> 

Paired with data showing high session refresh rates, this validates both the *behaviour* and *emotion* behind the problem.

# **Tips**

- Listen for *workarounds* - they’re strong indicators of unmet needs.
- Use a mix of observed behaviour and self-reported pain.
- Summarise top 3 validated insights and what evidence supports each.
