# Skill: pm-os setup

## Purpose
Get a new company or product from zero to a working `context/` folder in
one sitting. This is day one of a founding PM role: before writing a
single PRD, get what's in the founder's head written down where the
whole team (and every other skill) can use it.

## When to use
- First week in a new role, or first session with a founder
- `context/` is empty or still full of template placeholders
- The product has changed enough that context is lying (a pivot, a new
  segment, a pricing change)

## Inputs needed
- 45 minutes with whoever knows the product best (usually the founder)
- Anything already written: pitch deck, website, investor update, a
  Notion page, support tickets, a metrics dashboard. Read these first so
  the interview only covers the gaps.

## Step-by-step process

**1. Read before you ask.**
Go through whatever material exists and pre-fill a draft of each context
file. Mark every line as either `[confirmed]` or `[my guess]`. Founders
correct a wrong draft much faster than they fill a blank page.

**2. Run the interview, one file at a time.**
Ask in this order, because each answer sharpens the next:
1. **Product:** "Explain it to me like I'm a customer who's never heard of
   you." Then: "Who is it definitely *not* for?"
2. **Customers:** "Tell me about the last three customers you spoke to.
   What were they trying to do?" Push for real quotes, not summaries.
3. **Metrics:** "If you could only see one number every Monday, which
   one?" Then ask what would have to be true for it to go up.
4. **Bets:** "What's the team building right now, and what do you think
   it'll move?" Then: "How sure are you, out of ten?"
5. **Decisions:** "What's a decision from the last six months you'd hate
   to have to re-argue?" Log two or three.
6. **Glossary:** listen for words the founder uses that a new hire
   wouldn't understand, or that mean different things to different teams.
7. **Voice:** ask for one thing they've written that they're proud of.

Ask one question at a time. Wait for a real answer. If an answer is
vague ("SMBs", "engagement"), ask for the specific version before moving
on.

**3. Challenge as you go, gently.**
Setup isn't just transcription. Flag what you notice:
- A north star that measures activity rather than customer value
- Bets with no metric attached, or a metric with no bet driving it
- Two different answers to "who is it for" from two different people
- A "not doing" list that's empty (it never really is)
Write these into a short **Open questions** list rather than arguing
them out in the setup session.

**4. Write the files.**
Fill each file in `context/`. Keep it short. Date every number. Anything
still unconfirmed stays marked `[my guess]`.

**5. Play it back.**
Summarise the product in five lines using only what's in `context/`, and
read it to the founder. If they wince, something's wrong. Fix it there
and then.

## Output
- A filled `context/` folder
- An **Open questions** list (the five or so things you'd chase in the
  first two weeks)
- A suggested first skill to run next (usually Discovery on the biggest
  open question, or Product Review on whatever doc the team is working
  from today)

## Rules
- Never invent customer quotes, metrics or decisions to fill a gap. Leave
  it blank and put it on the open questions list.
- Strip anything sensitive before it goes in a file: no customer names
  without permission, no salaries, no credentials, no investor terms.
- Shorter is better. If a file is longer than a page after setup, cut it.

## Quality checklist
- [ ] Every file in `context/` has real content or a clear "unknown"
- [ ] North star has an exact definition and a dated baseline
- [ ] At least three verbatim customer quotes
- [ ] At least two decisions logged with reasoning
- [ ] "Not doing" list has at least one entry
- [ ] Open questions list exists and is short

## Hands off to
- **Discovery**: for the biggest open question
- **Product Strategy**: if there's no written strategy, or the bets don't
  add up to one
- **Weekly Product Review**: to set up the rhythm that keeps `context/`
  current
