01Discovery›

Purpose

Turn a vague signal, an exec ask, a support trend, a competitor move, into a scoped, evidence-backed opportunity worth sizing. Stops PMs from either chasing the wrong thing or jumping straight to solutions.

When to use

  • You've been handed a one-line brief and need to turn it into something actionable
  • A metric moved and you don't know why yet
  • Kicking off a new cycle and need a fresh opportunity backlog
  • Someone jumped straight to a solution and it needs pressure-testing

Process

  1. Restate the signal as a question, not a solution. "Add dark mode" becomes "why are users asking for this, what job is it serving?"
  2. Build an Opportunity Solution Tree. Outcome → opportunities (customer language) → solutions only at the leaves.
  3. Pull existing evidence before generating new evidence. Look for convergence across at least two independent sources.
  4. Apply a JTBD lens. Write the job story for the top 2-4 opportunities.
  5. Score and shortlist with ICE, directional ranking, not false precision.
  6. Flag what's still unknown, a "what would change our mind" list per opportunity.
  7. Write the one-page discovery brief. A decision document, not a research report.

Output

A discovery brief: reframed problem, opportunity tree, evidence summary with sourcing, job story, riskiest assumptions, recommendation.

Quality checklist

  • Problem stated as a need, not a feature
  • ≥2 independent evidence sources support the top opportunity, or the gap is flagged
  • Solutions are NOT decided yet
  • Riskiest assumption named explicitly
  • Someone can make a go/no-go call in under 5 minutes

02Market Sizing›

Purpose

Answer "is this big enough to matter" with a number you can defend in front of a CFO, not a vibe. TAM/SAM/SOM plus impact sizing, top-down and bottom-up so one checks the other.

When to use

  • Deciding whether a discovered opportunity is worth resourcing
  • Quarterly/annual planning, ranking opportunities
  • Building a business case where you own commercial/P&L framing
  • An exec asks "how big, really?" and gut-feel won't survive the room

Process

  1. Define the addressable unit precisely. "SMB merchants" isn't precise enough, state the segment exactly.
  2. Top-down TAM → SAM → SOM. State the formula and every input's source.
  3. Bottom-up cross-check. Build independently from current ARPU/take rate × addressable segment.
  4. Triangulate. If top-down and bottom-up are off by 10x, find out why before presenting either.
  5. Size the opportunity's impact via a driver tree, not just the market.
  6. Give a range, conservative / expected / optimistic, not a point estimate.
  7. Write the sizing doc, lead with the range and recommendation, maths after.

Output

Sizing doc: addressable-unit definition, TAM/SAM/SOM, bottom-up cross-check, driver-tree impact, scenario range, sourced assumptions.

Quality checklist

  • Every number traces to a source or is flagged as an assumption
  • Top-down and bottom-up both shown, gap explained
  • Addressable unit precise enough to reproduce
  • A range given, not a single point estimate
  • Ties to a metric the business actually tracks

03Customer Validation›

Purpose

Test whether real customers actually have the problem, and whether the proposed direction addresses it, before engineering time finds out the hard way. Covers problem and solution validation.

When to use

  • After Discovery produces a riskiest-assumptions list
  • Before writing a PRD for anything non-trivial
  • After Prototyping, to test a concept with real users
  • When a stakeholder is convinced and evidence is needed either way

Process

  1. Turn the riskiest assumption into a falsifiable test. State what evidence would prove it wrong, not just confirm it.
  2. Match method to assumption type: problem-exists → JTBD/switch interviews; willingness-to-pay → concierge/fake-door; solution-resonates → concept test; usability → moderated session on a prototype.
  3. Write the guide before recruiting. Ask about past behaviour, not hypothetical intentions.
  4. Recruit for the segment, not for convenience, include skeptics and non-users, not just power users.
  5. Run sessions with separated roles, one asks, one notes. Let silence sit.
  6. Synthesise across sessions, not within one, look for patterns across 5-8 conversations.
  7. Write the readout with a clear validated / invalidated / inconclusive call.

Output

Validation readout: assumption tested, method, sample, synthesised findings by theme, clear call, recommended next step.

Quality checklist

  • The assumption was falsifiable and could have been disproven
  • Questions asked about past behaviour
  • Findings synthesised across sessions, not one anecdote
  • Recruitment matched the target segment
  • Readout gives a clear call, including "inconclusive" if honest

04Prototyping›

Purpose

Make an opportunity tangible enough to react to, as cheaply as the question requires. The core discipline is matching fidelity to the question, not defaulting to the most impressive option.

When to use

  • After problem validation, to test whether a direction resonates
  • Before a full PRD, to de-risk direction with stakeholders cheaply
  • When engineering needs something concrete to scope effort
  • When a concept needs a usability pass before build

Process

  1. Name the ONE question first. Concept sense-check → sketch. Flow logic → low-fi wireframe. Feel/trust → high-fi mockup. End-to-end → coded/Wizard-of-Oz. Real behaviour → smoke test.
  2. Write the prototype brief before building, question, fidelity + why, scenario covered, what "useful signal" looks like.
  3. Build the smallest version that answers the question, resist extra polish and edge cases.
  4. Pick the test format, moderated for ambiguous concepts, unmoderated once the flow is concrete, in-context/smoke test for real behaviour.
  5. Run it via the Customer Validation method, same past-behaviour, don't-lead discipline.
  6. Separate user-reaction signal from technical-scoping signal if gathering both.

Output

A prototype at the chosen fidelity, plus a brief: question answered, fidelity rationale, scenario, and (post-test) findings.

Quality checklist

  • Primary question stated explicitly, fidelity matches it
  • Nothing built beyond what the question requires
  • Test format matches the concept's maturity
  • User-reaction and technical-scoping signal kept separate

05Experimentation›

Purpose

Design and read experiments that actually answer the question they're meant to, pre-registered and statistically sound, not a story fitted to the dashboard afterward.

When to use

  • Something's shipped and you need to know its real impact
  • Before launch, to pre-register success and avoid post-hoc metric shopping
  • Reading someone else's results and sanity-checking the conclusion
  • Prioritising which of several ideas to test first given limited traffic

Process

  1. Write a single-variable, falsifiable hypothesis. One primary metric, one primary change.
  2. Pre-register success criteria and decision rule before launch, the biggest defence against post-hoc rationalisation.
  3. Calculate sample size and duration up front. No peeking-and-stopping-early.
  4. Choose the right design, A/B, A/B/n, sequential/holdout, or pre/post with explicit confound caveats.
  5. Define guardrail metrics that must not move the wrong way even if the primary metric looks great.
  6. Run the full pre-registered duration, noting external events.
  7. Read against the pre-registered plan, not retroactively. Distinguish "no effect" from "no detectable effect at this sample size."

Output

Experiment design doc pre-launch, readout post-launch: hypothesis, MDE, sample/duration, design, guardrails, and the result read against the decision rule.

Quality checklist

  • Hypothesis names one mechanism, one primary metric
  • Success criteria written before results came in
  • Sample size/duration calculated, not eyeballed
  • Guardrails checked, not just the primary metric
  • Full duration run, or early stop explicitly justified

06PRD Generation›

Purpose

Turn a validated opportunity, a strategy, a roadmap item, a partial brief, or a conversation, into an implementation-ready PRD. An engineering team should be able to start building from the output immediately.

When to use

  • Writing a PRD, spec, or requirements document
  • Turning validated discovery/prototyping findings into user stories
  • Asked "what should we build" and the answer needs to be specific enough to hand to engineering
  • Reviewing someone else's PRD for gaps against the checklist below

Process

  1. Understand the context. Extract vision, users, pillars, in-scope features, constraints, success metrics from a strategy/roadmap, or gather the same via conversation.
  2. Define the product overview. One-sentence vision, problem statement, target users, success metrics.
  3. Write user stories, grouped into epics. "As a [user], I want to [action] so that [benefit]." 3-5 testable acceptance criteria each, MoSCoW priority, effort, strategic link. Sequential IDs (US-001...).
  4. Define functional requirements. Cover Auth, Core Features, Data Management, Integration, Reporting & Analytics. Every FR traces to a user story and strategic objective.
  5. Define non-functional requirements, with numbers. Performance, Security, Scalability, Reliability, Usability, Maintainability, each with a testable threshold, not a vibe.
  6. List open questions and risks, each risk with a mitigation.
  7. Run a final clarity pass before sharing, cut hedging and jargon.

Output

A PRD: product overview, epics of user stories with acceptance criteria, functional requirements, non-functional requirements with numeric thresholds, technical specs, constraints, success criteria, open questions and risks. See the PRD template below for the full structure.

Rules

  • Specific, not vague. "Fast" → "API responses <200ms at p95." Every requirement must be testable.
  • Traceability is mandatory. Every requirement links to a user need and a strategic objective.
  • Not everything is P0. Apply MoSCoW honestly, Must Have is the MVP, not a wish list.
  • Cover the unhappy paths. Error cases, edge cases, failure scenarios, this is where quality lives.
  • NFRs need numbers. No NFR without a testable threshold.
  • Preserve source language. Use the same terms the strategy/brief uses for segments, features, metrics.

Quality checklist

  • Product overview links to strategy (pillar, JTBD) or states there isn't one yet
  • User stories in correct format with 3-5 acceptance criteria each
  • MoSCoW prioritisation applied honestly, not everything Must Have
  • Functional requirements are specific and testable
  • NFRs have numeric thresholds, not "fast" or "secure"
  • Every requirement traces to a user story and strategic objective
  • Unhappy paths covered
  • Open questions and risks (with mitigations) listed

07Product Strategy System›

Purpose

Produce a product strategy that's evidenced, coherent, and actually usable for prioritisation, through four sequential phases, each with a human checkpoint before the next begins.

When to use

  • Setting or refreshing strategy for a product area, product line, or new bet
  • Onboarding into a product area and building the strategic picture from scratch
  • A roadmap keeps getting re-litigated with no written strategy to point back to
  • Company priorities shifted and the existing strategy needs re-testing

The four phases

  1. Gather Context, pull current performance, company-level priorities, competitive landscape, prior strategy, and known constraints into a facts-only context brief. No direction or opinions yet.
  2. Research, fill the specific gaps the context brief exposed. Let open questions drive the research, not a generic literature review. Mix external (market, competitors) and internal (customers, usage data) sources.
  3. Write, turn context + research into a specific, falsifiable point of view: where to play, how to win, what capabilities that requires, strategic pillars, success metrics, and what's explicitly out of scope.
  4. Review, a structured critique pass before it ships: falsifiable, evidenced, coherent, resourced, differentiated, and excludes something. Not "does this sound good."

Each phase has its own checkpoint, don't skip one to save time. A checkpoint is what stops bad context or weak research from silently propagating into the final strategy.

Output

A strategy document stating where to play, how to win, required capabilities, strategic pillars, success metrics, and exclusions, built through the Strategy Workspace template, phase by phase.

Quality checklist

  • Context brief is fact-only, reviewed before research began
  • Research answers the specific open questions from context, not generic
  • Strategy states where to play AND where it won't
  • "How to win" is specific enough to be wrong
  • Strategic pillars trace directly to the "how to win"
  • Success metrics have targets and a timeframe
  • The review pass happened as a distinct step, not folded into writing
  • Something was explicitly excluded or deprioritised

II

Frameworks reference

Opportunity Solution Tree

Desired outcome at the top → opportunities (customer language) as branches → solutions only at the leaves. If you're debating solutions before opportunities are agreed, go back up the tree.

Jobs-to-be-Done

People "hire" a product to make progress in a situation. Job story: "When [situation], I want to [motivation], so I can [outcome]." Use switch interviews to uncover the job behind a decision.

TAM / SAM / SOM

TAM = full opportunity at 100% penetration. SAM = reachable slice given your model today. SOM = realistically capturable within a time horizon. Always build top-down and bottom-up and triangulate.

ICE vs RICE

ICE = Impact × Confidence × Ease, fast, directional, good early. RICE = (Reach × Impact × Confidence) / Effort, better once reach is estimable from real usage data.

Riskiest Assumption Test

List every assumption an opportunity depends on. Identify the one that, if false, invalidates everything else. Test that one first, cheaply, before investing further.

Build–Measure–Learn / AARRR

Minimize the loop, not the build scope, fastest possible cycle through the smallest testable thing. Pirate Metrics (Acquisition, Activation, Retention, Referral, Revenue) checks which funnel stage an idea actually targets.

Method-picker: matching the test to the assumption

Does the problem exist / matter?JTBD interviews, switch interviews, support/churn analysis
Will people pay / prioritise this?Concierge test, fake-door test, pre-sales conversations
Does the solution direction resonate?Concept test, prototype walkthrough
Is a specific flow usable?Moderated usability test on a low/mid-fi prototype
Did the shipped change actually work?A/B test or sequential/holdout, pre-registered

A typical discovery run

How Might We → Crazy 8s → Assumption Map → Fake Door Test or Value Proposition Exercise → Story Mapping. That gets you from a fuzzy problem to a scoped v1 in about two weeks.

How much time do you have?

  • Under an hour → Hypothesis Statement, Assumption Map, Impact / Effort Map, Crazy 8s
  • An afternoon → Journey Map, Story Mapping, Value Proposition Exercise
  • Half a day → Project Kick-Off or Team Time
